For local E2E, configure `.env.local` using `.env.example`, start a disposable local PostgreSQL instance, generate the client, apply committed migrations, and seed the fictional test accounts. The tests use only configured `example.test` identities and create a fictional public request on each run. Local E2E writes must target a loopback/dev database only. Never use the E2E environment or demo seed against shared, staging-customer, or production data.

CI provisions isolated PostgreSQL 16 services for application checks and the container smoke job; neither connects to the WebDev-managed MySQL database or customer data. The application-check service uses trust authentication only inside its short-lived GitHub runner. The container smoke service uses a run-specific root password plus distinct, randomly generated/password-authenticated runtime and migration roles; role passwords and URLs are masked in logs. CI generates fresh Auth.js and demo-account passwords for each run rather than storing them in YAML. The workflow does not require a Production deployment credential or Gitleaks license. The Linux x64 Gitleaks archive digest is pinned in `.github/workflows/ci.yml` and was verified against the official release metadata and checksums; local execution used the matching ARM64 release archive.

## Full-history secret scan

The workflow first creates a disposable one-commit root history with a randomly generated fake GitHub token and confirms Gitleaks reports the expected rule; the temporary repository, patch, and scanner log are removed at job exit and the token is never added to the project. It then checks for reachable Git commits and pipes `git log --all --full-history --root -m -p --no-ext-diff --no-color` into `gitleaks stdin --redact --no-color --verbose` with shell `pipefail`. This includes root commits and merge-resolution diffs while ensuring Git or scanner errors fail the job. This avoids the root-parent range failure documented in the [Gitleaks Action issue tracker](https://github.com/gitleaks/gitleaks-action/issues/199).

## Audit trigger verification

The migration adds a PostgreSQL trigger rejecting UPDATE and DELETE on `AuditLog`. This was verified against a local seeded audit row: a same-value UPDATE was rejected with SQLSTATE `55000` and message `AuditLog rows are append-only.`; no audit row was changed. Database owners can still disable triggers, so this is not a substitute for external immutable archival.

## Non-blocking development-console notes

When the optional 3D scene is mounted in development, React Three Fiber 9.8.2 currently constructs `THREE.Clock`, which Three.js 0.186.1 marks as deprecated in favor of `THREE.Timer`. This upstream, non-fatal development warning does not prevent rendering or the passing 3D test; do not suppress it or patch installed package files. Reassess when a compatible upstream release is available. Framer Motion also prints an informational reduced-motion notice in development when the browser preference is enabled.

The supplied hydration diff showed extension-injected `<html>` attributes (`data-qb-installed`, `data-new-gr-c-s-check-loaded`, and `data-gr-ext-installed`). These are not emitted by the application; the issue was not reproduced during extension-free Chromium checks, and no broad hydration-warning suppression was added.

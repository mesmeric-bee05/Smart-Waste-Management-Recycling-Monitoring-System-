# Security model, controls and residual risks

## Information boundary

The app contains organization data (staff names/email and role, work schedules, weights/locations, and optional public request contact details). Location/time and resident requests may be sensitive even when sample data is fictional. Production operators must apply a documented retention, access, backup, deletion and incident-response policy under the customer's applicable law; this prototype does not provide legal/compliance advice or certification.

## Threats and implemented controls

| Threat                                  | Current control                                                                                                                                                                                                                                                                                                                                                   |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unauthorized role/tenant access         | Live DB user/organization revalidation; role checks on pages, server actions, services and protected export routes; query filters include `organizationId`; collector writes validate assignment; collection completion scopes point side effects to the actor's organization. Tenant relationships are not enforced with composite database foreign keys or RLS. |
| Credential guessing/account enumeration | Generic client sign-in error, Argon2id hashes, atomic account lockout counters, and a process-local IP/request throttle. Its current forwarded-IP header source is proxy-dependent and can be spoofed if ingress does not strip client-supplied headers; it is not a production-grade shared rate limiter.                                                        |
| Request abuse/resource exhaustion       | Strict Zod schemas, streamed 12 KiB public JSON cap, content-type validation, bounded list/export windows, row limit, parameterized Prisma queries and finite DB connection timeout/pool.                                                                                                                                                                         |
| XSS/content injection                   | React escaped rendering, no untrusted `dangerouslySetInnerHTML`, restrictive nonce-based CSP, output escaping in CSV, safe static map markers/popups.                                                                                                                                                                                                             |
| Session theft/replay                    | Auth.js signed short-lived database-role-revalidated JWT session configuration, `HttpOnly`/`SameSite`/`Secure` cookie settings and `Cache-Control: no-store` for sensitive responses.                                                                                                                                                                             |
| Accidental audit tampering              | Append events are transactionally paired with business writes; a PostgreSQL trigger rejects UPDATE/DELETE of `AuditLog`. Avoid sensitive payloads in metadata.                                                                                                                                                                                                    |
| Inaccurate synthetic/demo data          | Simulation and location provenance are persisted and labeled, with explicit no-live-device notices in UI/export.                                                                                                                                                                                                                                                  |
| Dependency/code exposure                | Exact package lock, `.dockerignore` exclusions, removal of `.env*` from Next standalone output before runtime-image copy, Next.js security headers, no production source maps, lint/type/unit/E2E/axe CI, checksum-pinned Gitleaks scanning all reachable history (including roots/merges), npm audit and Dependabot; CI actions are commit-pinned.               |

## Required production remediations

1. **Identity is not production approved:** `next-auth` 5.0.0-beta is a prerelease. The current Auth.js installation guide still instructs installing `next-auth@beta`; the application must remain gated until the customer approves a supported identity path and its callback, cookie, revocation, recovery and account-lifecycle behavior. Add MFA for privileged users where the selected provider supports it. The MVP has no self-service password reset or account verification.
2. Replace the per-process in-memory login/public-request limiter with a shared distributed limiter (e.g. a managed Redis/edge/WAF primitive), and configure trusted-proxy/client-IP handling explicitly. `src/server/rate-limit.ts` currently trusts the first `X-Forwarded-For` value without proving that a trusted proxy overwrote the inbound header; direct access or a preserving proxy can let clients rotate the value to evade the IP bucket. Keep account lockout as a separate control and test the final trusted ingress chain.
3. Provision production PostgreSQL with TLS certificate validation, least-privilege application and separate migration roles, network allowlists, backups/PITR and restore exercises. The sample Docker database and `.env.example` password are local-only. Do not make the seeded demo accounts available to production.
4. Provide stable secret storage and rotation for `AUTH_SECRET` and DB credentials. The build uses only throwaway example values. Do not pass live secrets as image build arguments or bake them into the client.
5. Confirm intended host/proxy trust, request origin/cookie policy, CSP allowlists and security headers against the actual Preview or production origin. `SameSite=None` is used for cross-site HTTPS Preview embedding only; prefer `Lax` on a normal same-site HTTPS site. Never infer Secure from `NODE_ENV`.
6. Tenant integrity is primarily application-enforced. The current migration does not add composite `(organizationId, id)` foreign keys or PostgreSQL RLS. Collection scheduling and public intake validate point ownership, and collection completion now uses a tenant-scoped `updateMany` that fails closed; retain those checks and add composite database constraints only through a separately reviewed, authorized additive migration.
7. Add external immutable audit export/retention/alerting if the customer's assurance level requires evidence beyond a trigger protected by normal application privileges. The database owner can disable triggers.
8. Complete a customer-specific privacy/data-classification review, threat-model walkthrough, independent penetration test and backup/recovery exercise before handling non-demo data.

## Security tests and incidents

CI covers unit/business invariants, serial E2E role restrictions, public intake, private report download and WCAG A/AA checks; it is not a penetration test. The local verification passed 24 unit tests, 8 Playwright scenarios, lint, strict type checking, formatting and an optimized production build; `npm audit --audit-level=moderate` reported zero vulnerabilities after the minimatch override. The final local ledger query was read-only and matched all three successful migration checksums to the approved SQL files. These checks do not verify Production connectivity, credentials, role grants, RLS, or hosting ingress. Re-run audits before releases. For suspected exposure: preserve logs, disable affected access through the identity/database operator, rotate compromised credentials via the secret manager, assess access to resident/request records and follow the customer's approved notification process. Do not delete/modify audit rows during incident handling.
